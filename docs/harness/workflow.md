# HARNESS WORKFLOW (MVP)

本文件定义本仓库的最小 harness 执行闭环：让任务可以稳定地「自动前进」，同时满足安全与质量约束。

---

## 1) 输入任务（Task Intake）

每轮只接入 1 个小任务（建议 0.5~1 天可完成），来源于 `docs/ROADMAP.md` 或明确 issue。

任务必须写成以下结构：

- **目标**：要达成的用户价值（一句话）
- **范围**：允许改动的目录/模块（例如 `packages/cli`）
- **非目标**：这轮明确不做什么
- **验收条件**：可被测试或命令验证的结果
- **风险点**：数据安全、隐私、兼容性、回滚风险

---

## 2) 执行步骤（Execution Loop）

对每个任务按顺序执行：

1. **拆解**：把任务拆成 3~5 个可验证子步骤
2. **实现**：按子步骤改代码/文档，避免一次性大改
3. **自检**：每完成一个子步骤就做局部检查（测试/命令/手工验证）
4. **收敛**：整理最终改动，确保与目标一致且未越界

执行中的协作要求（必须遵循）：

- 若目标/成功标准不清晰，先暂停并澄清，再继续执行。
- 默认持续评估是否存在更短可验证路径，而非按惯例推进。
- 若发现可显著降低时间、风险或改动面（经验阈值：约 >=30%）的替代路径，必须暂停并先向用户建议。

触发“路径优化暂停”时，输出固定为 4 点：

1. 当前路径的问题（1 句）
2. 更优路径（1 句）
3. 预期收益（时间/风险/复杂度）
4. 需要用户决策的选项与推荐项

执行时必须遵循仓库硬约束：

- `apply` 与写配置只允许 rename/copy 备份，禁止对用户目录做破坏性删除
- 不得暗示 zip 内容已自动脱敏

---

## 3) 验收证据（Verification Evidence）

任务完成前必须提交最小证据集：

- **测试结果**：`pnpm test`
- **相关子系统验证**（按改动选）：
  - CLI 改动：`pnpm run ocs -- <subcommand>` 的关键行为验证
  - Web 改动：构建/关键路径 smoke（按项目现状执行）
- **变更说明**：改了什么、为什么改、影响范围、剩余风险

若证据不足，任务视为未完成。

---

## 4) 失败回流（Failure Feedback）

任一步骤失败时，不允许停在“报错状态”，必须生成下一轮输入：

- **失败现象**：1~2 句描述
- **根因假设**：最多 3 条
- **下一步最小任务**：可在 0.5 天内验证
- **新增守门**：需要补的测试/CI 规则

失败回流产物应直接可被下一轮执行，不需要额外口头解释。

---

## 5) Done 定义（Definition of Done）

同时满足以下条件才算完成：

- 目标与验收条件均达成
- 必要测试通过
- 硬约束未被触碰
- 有完整的验证证据与剩余风险说明
- 失败场景有回流方案（如适用）

---

## 6) 首轮试跑建议（One-Task Pilot）

建议用一个小任务先试跑本流程（例如 CLI 的单点改进）：

1. 从 `docs/ROADMAP.md` 选一条可小步交付项
2. 严格按本文 1~5 节执行
3. 复盘三件事：
   - 哪一步最容易卡住
   - 哪类验证最缺失
   - 下次要自动化到 CI 的检查项

连续跑通 2 轮后，再扩展到并行任务或更大改动范围。
